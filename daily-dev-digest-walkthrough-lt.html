Daily Dev Digest Workflow

n8n workflow, kuris automatiškai paleidžiamas pagal nustatytą laiką, pasiima naujienas ir postus iš tavo RSS feed'ų, o tada naujausiu Gemini modeliu juos įvertina ir paruošia dienos suvestinę - naudingą kaip tik todėl, kad neapkrauna tavęs pertekline informacija. Žinutė nesiunčiama iš karto: n8n sukuria Draft'ą Gmail'e, kad galėtum peržiūrėti ir patvirtinti prieš siunčiant.

45–60 min n8n Cloud Gmail OAuth2 (draft'ams)
Trigger Feed pipeline AI pipeline

Ką išmoksi padaryti

Ko išmoksi

  • ✓Susikurti postų šaltinių sąrašą su Set node'u. Taip pat naudojamas Split Out - jis iškaido didelį sąrašą į atskirus item'us, todėl galime parsisiųsti daugiau postų lygiagrečiai. Naujo šaltinio pridėjimas niekada nereiškia naujo node'o.
  • ✓Paaiškinti n8n per-item vykdymo modelį: kai node'as gauna kelis item'us, jis savo logiką paleidžia atskirai kiekvienam iš jų, o gautus rezultatus vėl sujungia į vieną sąrašą.
  • ✓Sukuriamas AI prompt'as, pagal kurį vertinami post'ai naudojant naujausią Gemini modelį, o rezultatai grąžinami pagal JSON schemą.
  • ✓Vien AI modelio atsakymo neužtenka - jį reikia išparsinti (parse), kad ilgas modelio grąžintas tekstas virstų struktūrizuotais duomenimis, kuriuos vėliau galime panaudoti tolimesniuose workflow žingsniuose.
  • ✓Išmokti, kaip gautus rezultatus siųsti paštu, pvz., per Gmail. Sukursime Draft, kurį dar galima pataisyti, o žmogus pats nuspręs, siųsti ar ne - human in the loop.

Prieš pradedant

Keturi dalykai, kuriuos gera žinoti

Vykdymas kiekvienam item'ui

Node'as savo darbą atlieka atskirai su kiekvienu item'u, kurį gauna. Trys items įeina - trys fetch'ai išeina, iš vieno node'o.

Sąrašo išskaidymas

Split Out paverčia vieną item'ą su sąrašu į kelis atskirus item'us. Pvz., 1 item su 5 RSS post'ais taps 5 items - po vieną kiekvienam post'ui.

Modelio connector'is

Basic LLM Chain node'as leidžia prisijungti bet kurį palaikomą LLM modelį, kaip kad Claude, OpenAI ar Gemini. Naudojame Gemini dėl patogumo, bet galite lengvai pakeisti - per modelio connector'į.

Pasitikėk, bet patikrink

Modeliui verta duoti kuo mažiau autonomijos - jis gali haliucinuoti. Rūšiavimą, skaičiavimus ir kitą duomenų apdorojimą patikimiau atlikti kodu (JavaScript ar Python), o ne prašyti to iš modelio promptu. Šis workflow modeliu pasitiki tik įvertinimui - o rūšiavimą vis tiek tyliai perdaro kode.

Kūrimo eiga, node po node

Aštuoni node'ai, vienas pipeline'as

Sek žingsnius eilės tvarka, vieną po kito.

01Trigger

Pridėk trigerį - Schedule Daily

Schedule Trigger
Triggers the workflow on a given schedule
  1. Pridėk Schedule Trigger node'ą. Pervadink jį į Schedule Daily.
  2. Palik trigerio taisyklę numatytajame Interval režime ir nustatyk Trigger at Hour reikšmę į 8.
Kodėl

Kiekvienas workflow turi būti kažkaip paleidžiamas - kito kodo, tam tikru laiku, kito agento arba rankiniu būdu (pvz., Execute Workflow). Kitaip jis niekada nepasileis. Čia pasirenkame laiką: Interval režimas su valanda 8 tiesiog reiškia „vykdyk kiekvieną dieną 8 val. ryto“.

Checkpoint

Node'as rodo Interval režimą su Trigger at Hour nustatytu į 8, be klaidų.

02Feed pipeline

Susikurk feed'ų sąrašą - List of RSS Feeds

Edit Fields (Set)
Modify, add, or remove item fields
  1. Pridėk Edit Fields (Set) node'ą po Schedule Daily. Pervadink jį į List of RSS Feeds.
  2. Pridėk vieną lauką pavadinimu urls, nustatyk jo Type į Array, su reikšme:
urls (array)["https://dev.to/feed/tag/python", "https://dev.to/feed/tag/ai", "https://dev.to/feed/tag/productivity"]
Kodėl

Šis laukas atsako į klausimą „iš kokių šaltinių imu duomenis“. Naudojame tokį sprendimą, kad vėliau galėtume pridėti dar 5 linkus - tiesiog papildant šį lauką, be pasikartojimo ir be kodo keitimo.

Checkpoint

json.urls turi būti array su 3 elementais, ne tekstinė eilutė.

03Feed pipeline

Išskaidyk sąrašą - Split Out

Split Out
Turn a list inside item(s) into separate items
  1. Pridėk Split Out node'ą po List of RSS Feeds.
  2. Nustatyk Field to Split Out į urls.
Kodėl

Turėjome 1 item'ą su 3 URL sąraše. Split Out jį paverčia į 3 items - po vieną kiekvienam URL. Tada tolimesni node'ai kiekvieną apdoroja atskirai, patys.

Checkpoint

Testuojant grąžinami 3 atskiri items, kiekvienas su json.urls kaip viena URL eilutė.

04Feed pipeline

Parsisiųsk kiekvieną feed'ą - Retrieve Post Data

RSS Read
Reads data from an RSS Feed
  1. Pridėk RSS Feed Read node'ą po Split Out. Pervadink jį į Retrieve Post Data.
  2. Nustatyk URL į {{ $json.urls }}.
  3. Node'o nustatymuose įjunk Retry On Fail, Wait Between Tries 3000 ms.
Kodėl

Čia ir pasireiškia n8n per-item vykdymas: node'as gavo 3 items, todėl fetch'ą atlieka 3 kartus, po vieną kiekvienam URL - be jokio papildomo node'o.

Checkpoint

Testuojant grąžinama daug items, kiekvienas su title, link, pubDate, content arba contentSnippet.

05Feed pipeline

Išvalyk ir sujunk į vieną - Parse RSS data

Code
Run custom JavaScript or Python code
  1. Pridėk Code node'ą po Retrieve Post Data. Režimas: „Run Once for All Items“.
Parse RSS data - Code node// Ši funkcija išvalo teksto lauką nuo HTML žymių
function clean(raw) {
  if (!raw) return '';
  let text = String(raw);
  text = text.replace(/<(script|style|pre)[^>]*>[\s\S]*?<\/\1>/gi, ' ');
  text = text.replace(/<\/?(p|div|li|h[1-6]|br|tr|blockquote)[^>]*>/gi, '\n');
  text = text.replace(/<[^>]+>/g, '');
  return text.trim();
}

// Kiekvienam gautam item'ui paliekame tik reikalingus, jau išvalytus laukus
const items = $input.all().map(item => ({
  title: clean(item.json.title),
  creator: item.json.creator || item.json['dc:creator'] || '',
  link: item.json.link,
  pubDate: item.json.isoDate || item.json.pubDate,
  categories: item.json.categories || [],
  content: clean(item.json.content),
}));

// Sutraukiame viską į VIENĄ item'ą, kad kitas žingsnis matytų visą sąrašą iš karto
return [{ json: { count: items.length, items } }];
Kodėl sutraukti į vieną item'ą

Iki šiol viskas buvo po vieną item'ą kiekvienam straipsniui. Kitam žingsniui reikia visos partijos viename prompt'e, kad modelis galėtų straipsnius palyginti ir surikiuoti vienus prieš kitus.

Po dangčiu

Šis žingsnis sąmoningai nededublikuoja pagal URL - tai perduodama AI prompt'ui kitame žingsnyje, kuris gali pastebėti beveik identiškas, ne tik baitas-į-baitą vienodas, istorijas, tik jau ne taip nuspėjamai.

Checkpoint

Vienas item'as su json.count ir json.items - išvalyti straipsnių objektai.

06AI pipeline

Įvertink ir sudaryk suvestinę su Gemini - Digest & Scoring LLM

  1. Pridėk Basic LLM Chain node'ą. Prijunk Google Gemini Chat Model node'ą per modelio connector'į (jungiasi iš apačios, ne iš šono). Prijunk credentials ir aiškiai pasirink modelį.
  2. Nustatyk Prompt (User Message) į „Define“ režimą:
You are a technical newsletter editor. You will receive a JSON array of blog/RSS posts. Your job is to produce a digest. Score each post 0–100 on digest‑worthiness using this rubric: - Relevance (0‑40) - Depth (0‑25) - Timeliness (0‑15) - Actionability (0‑20) Deduplicate near‑identical stories - keep the best, note duplicate_count. Return ONLY valid JSON: { intro, top_stories[≥70, max 5], all_stories[all, sorted desc] } Here are today's posts ({{ $json.count }} total): {{ JSON.stringify($json.items) }}
  1. Node'o nustatymuose įjunk Retry On Fail, Max Tries 2, Wait Between Tries 5000 ms.
Kodėl svertinis rubrikas

Keturi pavadinti subkriterijai, sumuojantys iki 100, modeliui duoda konkretų karkasą vietoj nesuformuoto „įvertink 1–10“. Rezultatas - nuoseklesnis vertinimas skirtinguose paleidimuose, nors į schemą grįžta tik bendra suma.

Kodėl modelis dar ir rūšiuoja

Pakeisti „top stories = 70+“ į „80+“ vėliau yra vienos eilutės prompt'o pakeitimas, o ne kodo pakeitimas. Kompromisas - pasitiki, kad modelis surūšiuos teisingai, kuo kitas žingsnis pilnai nepasitiki.

Dažna klaida

Palikti Gemini Chat Model be credentials ar nepasirinkto modelio. Chain iškart nulūžta - visada konfigūruok patį sub-node'ą, ne tik chain node'ą.

Checkpoint

Testuojant grąžinamas text arba output laukas su kažkuo, kas atrodo kaip JSON - dar neprivalo būti idealiai švarus.

07AI pipeline

Apdorok AI atsakymą, sudėk laišką - Parse LLM Output

Code
Run custom JavaScript or Python code
  1. Pridėk Code node'ą po Digest & Scoring LLM.
Parse LLM Output - Code nodefunction parseDigest(raw) {
  let str = String(raw).trim();
  str = str.replace(/^```(?:json)?\s*/i, '').replace(/```\s*$/i, '');
  return JSON.parse(str);
}

const item = $input.all()[0];
const raw = item.json.text ?? item.json.output ?? item.json;
const digest = typeof raw === 'string' ? parseDigest(raw) : raw;

// safety net: sort all_stories by score desc in case the model didn't
const allSorted = [...digest.all_stories].sort((a, b) => b.score - a.score);

return [{
  json: {
    subject: `Dev Digest - ${digest.top_stories.length} top stories, ${allSorted.length} total`,
    html /* built from digest + allSorted */,
    text /* plain-text version */,
  }
}];
Kodėl tas ?? grandinėlė

item.json.text ?? item.json.output ?? item.json apsaugo nuo neaiškumo dėl lauko pavadinimo, ne nuo blogo turinio - skirtingos LLM chain node'o versijos savo output lauką pavadina skirtingai.

Kodėl vis tiek perrūšiuoti kode

Prompt'as jau prašė rikiuoti mažėjančia tvarka - bet vietoj to, kad tiesiog pasitikėtų, ši eilutė atlieka pigų, determinuotą perrūšiavimą, kad garantuotų vienintelį invariantą, nuo kurio realiai priklauso laiško išdėstymas.

Pastebėk spragą

Čia nėra try/catch. Jei JSON.parse meta klaidą, šis node'as taip pat lūžta ir visas vykdymas žlunga be jokio sukurto draft'o - pagrįstas supaprastinimas prototipui, bet vertas sustiprinti vėliau.

Checkpoint

Vienas item'as su subject, html, text, topStoryCount, totalCount. html turi tavo tikrus pavadinimus, įvertinimus ir nuorodas.

08Delivery

Sukurk Gmail draft'ą - Create Digest Draft

  1. Pridėk Gmail node'ą. Nustatyk Resource į Draft (ne Message/Send).
  2. Nustatyk Email Type į HTML, Message į {{ $json.html }}.
  3. Options → Send To įrašyk savo adresą. Prijunk Gmail OAuth2 credentials.
Kodėl draft'as, ne send'as

Draft'as laukia tavo Drafts aplanke, kol žmogus peržvelgs ir paspaus siųsti - protingas numatytasis pasirinkimas, kol dar kuri pasitikėjimą AI sugeneruotu turiniu. Perjungimas į Send vėliau yra vieno lauko pakeitimas.

Dažna klaida - ir reali šiame konkrečiame node'e. Parse LLM Output suskaičiavo tikrai naudingą subject eilutę ir įdėjo ją į $json.subject - bet jei čia Subject paliktas kaip statinis tekstas, ta reikšmė niekada nenuskaitoma:

Dažna klaida

Įrašytas gavėjo adresas Send To lauke lengvai pamirštamas pakartotinai naudojant bendrą workflow - įskaitant šitą. Visada patikrink prieš naudodamas pakartotinai.

Checkpoint

Po pilno test paleidimo tavo Gmail Drafts aplanke (ne Inbox) atsiranda naujas draft'as su pataisytu dinaminiu subject ir suformatuotu HTML turiniu.

Pilnas paleidimas

Testuok visą pipeline'ą

Paspausk Test workflow ir stebėk, kaip kiekvienas node'as užsidega eilės tvarka:

Schedule Daily → List of RSS Feeds → Split Out (3 items) → Retrieve Post Data → Parse RSS data → Digest & Scoring LLM → Parse LLM Output → Create Digest Draft

Atsidaryk Gmail Drafts aplanką ir patikrink, ar draft'as sukurtas, subject atspindi tavo Step 8 pataisymą, o HTML turinys parodo realius straipsnius su veikiančiomis nuorodomis. Jei kuris nors node'as šviečia raudonai - paspausk jį, klaidos panelė nurodys, kuri išraiška nepavyko.

Pasiimk su savimi

Geriausios praktikos

Mastas

Rinkis duomenimis paremtą sąrašą vietoj hardcoded lygiagrečių node'ų, kai šaltinių gali daugėti.

Pasitikėjimas

Kai rūšiavimą, ribas ar dedup'inimą perduodi promptui, kode pridėk pigų saugiklį tam invariantui, kuris tikrai svarbus.

Pakartotinis naudojimas

Hardcoded gavėjo adresus ir statiškas subject eilutes traktuok kaip dalykus, kuriuos reikia patikrinti, o ne aklai pasitikėti - šis workflow turi abu.

Versijos

Output lauko pavadinimo neaiškumą apdorok atsargiai, taip kaip text ?? output ?? json.

Prototipas

Klaidų apdorojimo trūkumas yra pagrįstas supaprastinimas pirmam bandymui - bet tai pažymėk ir sustiprink, prieš pradedant juo remtis kasdien.

Pristatymas

Kol nepasitiki AI sugeneruotu rezultatu, rinkis žmogaus peržiūrą (draft'ą) vietoj pilnos automatizacijos.

Praplėsk workflow

Papildomi iššūkiai

  • 1

    Pataisyk subject sujungimą

    Nustatyk Subject į {{ $json.subject }} - mažiausias ir konkrečiausias pataisymas visoje laboratorijoje.

  • 2

    Pridėk fallback'ą į Parse LLM Output

    Apgaubk parseDigest(raw) try/catch: sudaryk minimalią suvestinę iš žalių straipsnių, kad ir netvarkingas atsakymas vis tiek sukurtų draft'ą.

  • 3

    Apriboki iki darbo dienų

    Perjunk Schedule Daily į Cron Expression režimą: 0 8 * * 1-5.

  • 4

    Pridėk ketvirtą feed'ą, be jokių naujų node'ų

    Pridėk dar vieną URL į urls array ir paleisk iš naujo - įsitikink, kad teka 4 items be jokių kitų pakeitimų.

  • 5

    Pereik nuo draft'o prie send'o

    Pakeisk Resource į Message (Send), kai jau pasitiki suvestine - nebūtina, bet gali apsaugoti Slack patvirtinimo žingsniu.

Pasitikrink save

Žinių patikrinimas

Kodėl naujo RSS šaltinio pridėjimas reikalauja tik urls array redagavimo, o ne naujo node'o?
Šaltinių skaičius nėra užkoduotas node grafe - jis priklauso nuo to, kiek įrašų yra urls. Split Out tą array išskaido į po vieną item'ą kiekvienam URL, o Retrieve Post Data (per per-item vykdymą) automatiškai parsisiunčia po vieną feed'ą kiekvienam item'ui, tad node'ų skaičius niekada nesikeičia.
Ką daro Split Out, ir kodėl Retrieve Post Data parsisiunčia tris feed'us turint tik vieną RSS Feed Read node'ą?
Split Out vieno item'o urls array paverčia trimis atskirais items, kiekvienas su viena URL. Retrieve Post Data savo fetch'ą paleidžia po kartą kiekvienam gautam item'ui - trys items reiškia tris HTTP fetch'us, nors fiziškai tai vienas node'as.
Prompt'as jau prašo modelio surūšiuoti all_stories - kodėl vis tiek perrūšiuoti kode?
Prompt'o instrukcijos nėra garantija - modelis kartais gali grąžinti neteisingą tvarką, net kai aiškiai paprašyta. Perrūšiavimas kode yra pigus ir determinuotas, tad pašalina bet kokią riziką laiško straipsnių tvarkai, nereikalaujant pasitikėti modelio paklusnumu kiekvieną kartą.
Kiekvienas draft'as turi tą pačią subject eilutę, nesvarbu kiek top stories rasta - ką patikrinti pirmiausia?
Ar Create Digest Draft Subject laukas realiai nurodo į {{ $json.subject }}, ar tai tik statinis placeholder tekstas - reikšmė gali būti teisingai suskaičiuota anksčiau, bet niekada nepasiekti lauko, kuris turėtų ją parodyti.

Santrauka

Ką šis pattern'as apibendrina

Susikūrei workflow, kuris vieną konfigūruojamą RSS feed'ų sąrašą paverčia kasdiene, AI įvertinta suvestine - naudodamas duomenimis paremtą fan-out, kad atskirtum šaltinių skaičių nuo node'ų skaičiaus, svertinį rubriką nuosekliam vertinimui, atsargų parsinimą sugadintiems ar kitaip suformuotiems AI atsakymams, ir peržiūra-pirma pristatymo žingsnį. Ta pati struktūra tinka konkurentų pranešimų sekimui, klientų atsiliepimų suvestinei ar mokslinių straipsnių kuratoriui - tik pakeisk šaltinių sąrašą ir pritaikyk rubriką.
